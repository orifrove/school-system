# Рабочее место администратора

Используется существующий Django Admin по /admin/. Это улучшение текущего
интерфейса, не завершение запланированной отдельной React-панели.

## Приглашения

Откройте Users → Invite codes → Add. Форма предлагает случайный код
и срок действия на семь дней вперёд; их можно изменить перед созданием.
Выберите активного пользователя без Telegram-привязки. Создатель записывается
автоматически из текущей учётной записи администратора.

Форма не принимает активный код с истёкшим сроком. У существующего кода
нельзя сменить сам код или пользователя. used_at редактировать нельзя;
погашенный или аннулированный код не переводится обратно в active через Admin.
Для нового приглашения аннулируйте старое активное, затем создайте новое.
В списке видно, истёк ли срок; доступен поиск по коду и пользователю.

Роль назначается отдельно в User → User roles. Приглашение не назначает роль.
Учётная запись Django Admin и бизнес-роль Admin — разные механизмы доступа.

## Подключить родителя

1. Создайте User родителя и назначьте роль Parent.
2. Откройте Education → Students → нужного ученика.
3. В блоке Parent students добавьте родителя и вид родства, сохраните.
4. Создайте приглашение для родителя и передайте ему код согласованным способом.
5. После активации родителю доступны /menu → «Мои дети» и /children.

Новая связь не сохраняется, если выбранный пользователь неактивен или не
имеет роли Parent. История зачислений видна в той же карточке как отдельный
блок со ссылками на записи; напрямую в этом блоке она не редактируется.

## Группы и расписание

В списке групп работает поиск по группе, предмету и имени учителя.
В карточке группы видны зачисления. При назначении нового преподавателя
проверяются активность пользователя и роль Teacher.

Смена учителя через GroupAdmin вызывает существующие update_group и
change_group_teacher: planned-занятия обновляются, held/cancelled сохраняют
исторического преподавателя. Предмет группы с Enrollment или Schedule
нельзя сменить — форма предлагает создать новую группу.

В форме Schedule проверяются порядок времени и дат действия. Поле Enrollment
принимает только индивидуальное обучение; для группы используйте Group.
Проверки расписания описаны здесь именно для формы Admin, а не как новые
ограничения БД. Работа через произвольный ORM требует отдельной проверки.

## Поиск учебных записей

- Ученики: поиск по имени, фильтр активности, число активных зачислений.
- Посещаемость: поиск ученика или предмета, фильтр статуса, навигация по дате занятия.
- Оценки: поиск ученика или преподавателя, навигация по дате выставления.
- Занятия: фильтры статуса/предмета и навигация по датам.
- Связи родителей: поиск по имени родителя или ребёнка.

Связанные объекты загружаются вместе со списками, чтобы не делать отдельный
запрос на каждую строку. Ученики, группы и зачисления показываются по 30 строк.

Прямое изменение оценок и посещаемости в Admin пока не формирует очередь
уведомлений: эти события создают education.services, используемые ботом.
Подробности отправки — [NOTIFICATIONS.md](NOTIFICATIONS.md).

## Начисления и платежи

В Billing → Billing periods видны начисление, внесённая сумма, остаток,
переплата и фактическое состояние оплаты. Фильтр позволяет выбрать
неоплаченные, частично оплаченные, оплаченные периоды или периоды с переплатой.
Нулевые начисления и переплаты входят в «Оплачено». Расчёт общий с родительским
меню: сумма нескольких платежей не дублирует начисление.

Новое начисление создаётся вручную для зачисления. Сумма не может быть
отрицательной, конец периода — раньше начала. После сохранения зачисление,
даты и сумма доступны только для чтения, чтобы сохранить исходное начисление.
В карточке показана история платежей со ссылками на отдельные записи.

В Billing → Payments выберите период, укажите положительную сумму и дату.
Также можно открыть начисление и нажать «Зарегистрировать платёж»:
период будет выбран, а положительный остаток подставится в сумму.
Её можно изменить для частичной оплаты. Для закрытого периода сумма
остаётся пустой. Кнопка доступна только сотрудникам с правом добавления
Payment; подстановка требует также права просмотра начислений.
Каждое открытие формы заново читает баланс, но после открытия он может
измениться — перед сохранением проверьте сумму, особенно при одновременной
работе нескольких администраторов. При ручной смене периода перепроверьте
сумму: автоматического пересчёта в открытой форме пока нет.
Переход по кнопке не создаёт платёж; запись появляется после сохранения.
Дата по умолчанию — текущий момент. Автор автоматически берётся из текущего
администратора и сохраняется при исправлении платежа; изменения фиксируются
стандартным журналом Django Admin. Доступны поиск по ученику/комментарию и
навигация по дате. Исправление и удаление платежей остаются доступны согласно
обычным правам Admin; отдельный процесс возвратов пока не реализован.

Состояние оплаты вычисляется при чтении; сохранённое поле `status` не
редактируется формой и не синхронизируется автоматически. Другой код,
читающий это поле напрямую, не должен считать его фактическим балансом.
Ограничения формы и неизменяемость начисления относятся к Django Admin;
произвольные ORM-записи не получают новых ограничений. Миграций нет.
